# Game compiler and native player

The root `Compiler/` package is a development tool, packaged as an independent x64 `BazzaltCompiler.exe` using Nuitka. Editor integration uses asynchronous `QProcess` and ASCII-escaped newline-delimited JSON stage events (lossless Unicode through Windows legacy pipes), displayed in a modal progress dialog. The final completion event is emitted after publication/cleanup and before launching; game stdout/stderr cannot inherit the compiler protocol pipe. No compiler implementation, editor module, Python binary, Qt dependency, or source script is shipped in the game payload.

## Boundaries

- `Compiler/settings.py`: versioned per-project schema, validation and security presets. Never add a raw secret field here.
- `Compiler/build.py`: project build lock, matching prebuilt runtime validation, target-specific native script compilation, external cooker, custom shader cooking, PE production resources, final output ownership and publication.
- `Compiler/native/Cooker.cpp`: x64 headless host for the existing native import pipeline. It never initializes Filament. All invalid imports are fatal to a production cook, unlike editor project opening.
- `AssetDatabase::ExportCooked` and `Engine::ExportCookedProject`: immutable UUID index, asset products, scenes rewritten to stable script references, native module registration. Source projects are not rewritten.
- `Compiler/native/Player.cpp`: Win32 window, native input events forwarded into SDL-backed InputAccess, game viewport (never Scene view), resize, rendering, scripts, audio, teardown. `--verify-package` validates content without GPU initialization; `--smoke-test` exercises three hidden game frames.

`BuildSettings.json` is beside the project file. Work is under `.bazzalt/Cache/Build`; final outputs are in `bin`. Settings contain production/version/license metadata, x86/x64 target, startup scene, runtime directory, window options, ZIP output, BPAK/loose format, chunk size, padding, encryption and key delivery. Output ownership markers contain a path hash, not the developer's absolute project path.

## Native startup and windowing

Window modes are windowed, maximized, borderless-sized, and fullscreen desktop on the primary monitor. The player paints black from its first native erase/paint messages. An owned native cover (not a Filament child surface) displays the centered brand over the client area while extraction, initialization and warm-up occur. The renderer records successful viewport submissions; a bounded `flushAndWait` gates cover removal. Editor-only frames warm the scene without running gameplay scripts. Intro controls are enabled, minimum duration, logo size and allowing input to skip; skipping cannot bypass frame readiness. The SVG source is `Launcher/BazzaltLogo.svg`, rasterized once by `embed_game_logo.py` and embedded into the executable as BGRX pixels; Qt is build-time only. Smoke tests bypass the minimum timer, not the readiness gate.

## BPAK v3 and protected manifests

New chunks start with `BZPAK003`, preserving the v2 little-endian 29-byte `<IIIQQB` header: stored path length, stored payload length, decoded length, decoded file offset, total decoded size and flags (encrypted=1, compressed=2, alias=4). Paths in encrypted records are also AES-GCM encrypted: path nonce (12), ciphertext, tag (16), authenticated with the header. Payload AAD is header + stored encrypted path. Following the path are payload nonce (12), tag (16), digest (32) and payload. For unencrypted records the digest is SHA-256; encrypted v3 uses HMAC-SHA256 with a domain-separated digest key, avoiding exposed plaintext fingerprints. Segment bounds, XPRESS-Huffman compression and alias rules remain: at most 4 MiB decoded bytes, exact decompressor output length, aliases only to previously completed files of the same size. The reader retains legacy v1/v2 decoding, but new builds require version-3 runtime templates and signature seals. See [the security protocol](game-build-security.md) for exact key/envelope details. Windows Cabinet supplies compression; no codec DLL is redistributed.

The Windows player uses system BCrypt AES-GCM/SHA-256/HMAC/ECDSA-P256 and DPAPI; the compiler uses cryptography's AESGCM/HKDF APIs. Every encrypted build has a fresh random data key wrapped under a separate delivery key. HKDF-SHA256 separates wrapping, package, configuration and inventory keys. Embedded and sibling delivery keys remain recoverable; environment delivery keeps the master outside the build. Optional `dpapi_user` protects the delivery key for the building Windows account and is not a portable distribution mode. Native key buffers are wiped during normal and exception unwinding; the separate Python compiler process can contain transient immutable secret copies until exit, so do not claim complete tool-memory zeroization.

`game.bootstrap` contains only signed bootstrap parameters, player/seal hashes and the wrapped key. `game.integrity` contains output-file hashes and full decoded-file hashes; `game.json` contains game configuration. Configuration and inventory are AES-GCM envelopes when Encrypt configuration and inventory is enabled, as it is by default for encrypted presets and migrated older encrypted profiles. `game.signature` signs the domain-separated, length-framed bootstrap plus stored inventory. The executable's `BZSIG003` seal pins the verification key; its private key exists only during building. Verification checks normalized executable bytes (excluding PE checksum/certificate-directory fields), the complete seal, every signed output file, and decoded files after extraction. File/directory leases reject reparse points and deny write/delete/replacement while content is in use. Engine DLL loading remains delayed until verification; OS/CRT loader code still runs first. This is not publisher authentication or a replacement for Authenticode. High and Very high have the same cryptographic strength.

The player checks framing, safe relative paths, case-folded duplicates, segment order, file sizes, integrity and complete files. Bounds: 4 MiB segments, 4096-byte paths, 1 million records, 8 GiB per extracted file, 32 GiB total extraction. Extraction is a unique per-process temporary directory; engine destruction precedes directory cleanup. Normal shutdown deletes plaintext. New sessions exclusively lock a versioned ownership marker; subsequent player launches reclaim abandoned marked UUID directories, skipping active, unowned and reparse-point trees. A crash can leave plaintext until the next launch; VFS/streaming remains a separate architectural change. Legacy unmarked temporary/build directories are deliberately not removed automatically.

Presets are relative configurations, not secrecy guarantees. Embedded/sibling keys are recoverable; players can inspect decrypted memory and temporary files. Padding is not authentication. Unencrypted SHA-256 is corruption detection only. No online key server, code signing, DRM, sandbox, or anti-cheat is implemented. Document these limits when extending settings.

## Releases and verification

Cook workspaces are disposable and removed on success or failure. Under the project build lock, subsequent builds reclaim abandoned explicitly marked workspaces. Incremental scripts remain separate; ZIP Build and Launch retains one owned launch image. Older unmarked GUID staging directories are not automatically deleted. Cooking exports current import products and explicit glTF dependencies rather than whole UUID folders with obsolete generations. Source copies are still retained for runtime path consumers, but BPAK aliases eliminate byte-identical payload duplication. Extracted/loose copies still occupy their decoded disk size; 64 MiB is a chunk ceiling, not a promised compression ratio.

Opt-in inclusion/exclusion patterns filter only the disposable cooked output. Serialized UUID/path references in scenes, material instances, mixers and texture descriptors form a dependency closure. Startup is retained; an explicitly excluded required dependency is an error. Dynamic script loads need explicit inclusion rules. Imports/native script validation still happen before filtering, so excluded broken source assets can still stop cooking.

The editor sends `cancel\n` on compiler stdin. A daemon control reader sets an event checked between tool stages, shader assets, package segments and archive entries. No tool is forcibly killed; cancellation can wait for the current external tool step. Publication is a transaction boundary: cancellation is checked immediately before it, then disabled in the editor. Cancelled builds emit `cancelled` and exit 2 only after workspaces unwind; they never launch or publish partial output.

Build asset roots must be dedicated project subdirectories, never the project root, `bin` or `.bazzalt`. This prevents builds from indexing their own output and cache trees.

Plaintext extraction directories have a protected Windows ACL granting access only to the launching account and SYSTEM, inherited by extracted files. Control characters in package paths and zero-progress nonempty segments are rejected. These changes do not implement a VFS, publisher certificate signing or DRM, and do not hide plaintext from the launching account or administrators. The settings UI omits the explanatory paragraph; the security limits above still apply. See [the limitation register](game-build-limitations.md) for remaining work.

CI builds the native player for both Windows architectures, and the cooker only for x64. `stage_game_runtime.py` copies binaries and the target ScriptSDK into `RuntimeTemplates/windows-{x64,x86}` and checks PE machine types. Core releases carry their runtime template; x64 Editor releases include x64 runtime and standalone compiler/cooker tools. Install the x86 Core template separately and select it in Build Settings. Large dependencies are built by existing CI workflows, never by the content compiler.

Run `python -m unittest discover -s Compiler/tests -v`, editor tests, and CTest. Native integration tests consume the already-built runtime, build and verify encrypted/unprotected games and ZIPs, and reject tampered packages. `game-compiler.yml` runs tool unit tests independently. Test changes in clean packaged editor distributions too: Nuitka tool dependencies must remain outside game outputs.
