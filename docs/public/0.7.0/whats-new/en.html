What's new in 0.7.0

This release adds Linux support, custom drawing through the C++ and Lua Graphics APIs, and ordered camera material effects. It also improves editor startup and documentation loading. Existing Windows projects remain compatible.

Custom drawing in C++ and Lua

Use #include <Bazzalt/Graphics.h> in C++ or Bazzalt.Graphics in Lua to submit your own geometry without accessing renderer internals. A GraphicsVertex contains position, normal, UV coordinates and color. GraphicsTopology supports points, lines, line strips, triangles and triangle strips.

  • CreateMesh creates reusable geometry. GraphicsMesh.SetGeometry replaces its vertices and indices; getters expose geometry and revision information, and Destroy invalidates the shared mesh handle.
  • DrawMesh submits a mesh with a material and transform. DrawVertices submits geometry directly; DrawLine and DrawTriangle provide simple vertex-color drawing. Submissions last one rendered frame. ClearDraws clears queued submissions, and IsAvailable checks whether rendering is initialized.
  • GraphicsDrawOptions controls camera selection, layer masks, priority and shadow participation. Default drawing uses an unlit vertex-color material; compatible surface materials can supply custom shading.
  • GraphicsEvent exposes the scene, camera, viewport dimensions and camera matrices. Use these matrices to position custom 2D geometry or draw with an orthographic camera.

Rendering events

Subscribe through Subscribe or the named helpers: OnBeginFrame, OnCameraResize, OnBeforeCamera, OnBeforeDraw, OnAfterDraw, OnAfterCamera and OnEndFrame. Unsubscribe removes a listener. Supply an entity owner when the subscription should expire with that entity.

Submit drawings during gameplay updates, OnBeginFrame or OnBeforeCamera. Camera callbacks automatically scope their submissions to that camera and viewport. Other callbacks are notifications; an after-render notification does not mean the GPU has finished. See the C++ drawing guide and Lua drawing guide for examples, limits and callback lifetimes.

Ordered camera material effects

A camera can now apply up to 32 ordered material passes. Each CameraMaterialPass holds a material asset and an enabled flag. The output of one enabled pass becomes the input of the next, allowing effects to be combined for game views and camera render textures.

CameraPostProcessing adds AddMaterial, SetMaterials, SetMaterialAt, SetMaterialEnabled, RemoveMaterial, MoveMaterial, ClearMaterials and GetMaterials in both C++ and Lua. Method indices start at zero; arrays returned to Lua start at one. The existing SetMaterial API still works and replaces the stack with one material. Older scenes with a single material continue to load.

In the camera inspector, use Post Process Materials to add a pass, choose a project material, enable or disable it, change its order, or remove it. These edits support undo/redo and preserve entity selection. Pass materials must be canvas-compatible. See camera material effects, the C++ reference and the Lua reference.

Editor startup and native dialogs

Editor startup blocks interaction until initialization and the attached viewport are ready, discarding queued input before enabling the editor. File selection uses platform-native dialogs. Branding is shared across the editor and Hub.

Faster documentation loading

Pages no longer load the full search text for every release on startup. The home page uses a small catalog, guides load navigation only for their version and language, and search data loads when search is opened. Search results are bounded to keep large API references responsive. Navigation, language/version selection and search continue to work offline using local files.

Linux support

Hub, Editor, core SDK, game compiler, content cooker and standalone player now have Linux build and release paths. The editor and player use X11; Wayland desktops can run them through XWayland. Vulkan and OpenGL remain selectable. Linux games include native runtime libraries and cooked content, with no Python or editor dependency.

The Linux player includes window modes, keyboard/mouse/text input, the startup logo, frame limiting and application lifecycle events. Content protection uses OpenSSL for the same AES-GCM, HKDF, SHA-256 and ECDSA scheme as Windows. Linux packages use Zstandard compression. See the Linux installation and development guide.

Platform-aware build settings

Build Settings now includes Windows and Linux platform choices. A warning explains unsupported host/architecture/security combinations. Build and Build and Launch reject these combinations through the editor Console before cooking or launching anything. Build on the target OS using a matching runtime SDK. Windows x64/x86 output remains supported; Linux output supports x64 and x86 through separate runtime SDKs.

CI and releases

A Linux badge and workflow cover native builds, editor and Hub tests, compiler tests, encrypted-package verification and GPU smoke tests under Xvfb. Release packaging creates separate Linux Core, Compiler, Editor and Hub ZIP archives and combines Windows/Linux entries into the Hub download catalog. ELF architecture and executable permissions are validated during installation.

Platform differences

Native Wayland surfaces and cross-OS game compilation are not supported in this release. Windows account-bound DPAPI keys remain Windows-only; choose embedded, file or environment key delivery on Linux. POSIX file leases are advisory and do not provide Windows deny-write semantics. Client-side content protection does not prevent an owner from patching their executable. Linux binaries require the libraries and baseline distribution listed in the Linux guide.

Platform and backend reference

The new support tables distinguish Windows/Linux editor and game-output targets, architectures, rendering backends and unsupported mobile, Apple, browser and console targets. The README includes the same support overview.

Extension packages and SDKs

Window > Extensions manages editor-wide .bpack imports, enablement and project SDK pins. Build > Build Package validates YAML manifests and compiles Lua/native scripts against a supplied SDK. Extensions can contribute themed .ui docking panels, menu actions, COMPONENT behaviors and serialized scene settings.

C++ adds Bazzalt/Extension.h with Extensions, ExtensionRegistry and typed function exports; Lua adds Bazzalt.require and Bazzalt.Extensions. Scene extension-property methods persist custom namespaced settings. Runtime SDKs and private helpers enter protected game content under ext; editor-only controllers and UI stay out of the player. See the separate Extensions authoring reference and user manual.
