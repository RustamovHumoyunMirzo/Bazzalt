Entities and components

An entity is a handle to a scene object. Components provide that object's data. A handle can become invalid when its scene or object is destroyed.

Get or create an entity

#include <Bazzalt/Scene.h>
#include <Bazzalt/SceneManager.h>
#include <Bazzalt/Components/PrimitiveObject.h>

void CreateCube() {
    auto* scene = Bazzalt::SceneManager::GetActiveScene();
    if (!scene) return;
    auto cube = scene->CreateEntity("Cube");
    cube.AddComponent<Bazzalt::PrimitiveObject>();
}

This helper is called from gameplay, not an application entry point. An entity receives the engine's required identity, name, hierarchy, and transform data. AddComponent adds the requested component type; it does not add a duplicate of an existing type.

Use IsValid() before using a handle that may outlive a scene change. UUID lookup is suitable for stable references. Name lookup can be convenient, but two entities may have the same name.

Read and change components

if (auto* light = entity.TryGetComponent<Bazzalt::Light>()) {
    light->Intensity = 1000.0f;
}
entity.SetComponentEnabled<Bazzalt::Light>(false);

The snippet assumes you include Bazzalt/Components/Light.h and the entity is valid. TryGetComponent returns null when that type is absent. GetComponent expects the component to exist. Enabling a component is different from removing it: disabling retains its values for use when enabled again.

C++ component references point into scene storage. Do not keep them across component removal, entity destruction, or scene replacement. Lua uses copied values instead; its write-back rules are described in Lua conventions.

Parenting and world transforms

child.SetParent(parent);       // Keep the current world transform.
auto world = child.GetWorldTransform();
world.Position.Y += 1.0f;
child.SetWorldTransform(world);
child.RemoveParent();          // Return to the scene root, keeping world placement.

Transform component values are local to the parent. World values compose the child's local transform with all its ancestors. This is why moving a parent moves its child even without editing the child's local position.

SetParent and RemoveParent default to preserving world placement. Pass false for worldPositionStays if you intentionally want to keep the local values instead. Cross-scene parenting and hierarchy cycles are rejected. UUID zero represents the permanent root, not an ordinary deletable object.

Define your own data component

#include <Bazzalt/Component.h>

struct Health : Bazzalt::Component {
    float Current = 100.0f;
    float Maximum = 100.0f;
};

// Inside gameplay code:
// entity.AddComponent<Health>();

Custom component types derive from Component. A System can process them, while an attachable COMPONENT behavior can access them through its entity. The compiler knowing a C++ struct does not automatically register its fields with the editor, scene serializer, or Lua binding layer. For Inspector-editable script fields, use PROPERTY in an attachable behavior. For an engine extension, register the corresponding serialization and Lua support explicitly.

Queries and lifetime

Scene provides Pick, PickAll, Raycast, RaycastAll, and overlap queries against scene geometry. These are scene queries, not a physics simulation or a promise of rigid-body collision behavior. Imported model hierarchy and primitive geometry can be queried without creating a physics world.

DestroyEntity destroys descendants as well. Do not continue using their handles after destruction. Modifying scene structure during a component iteration requires care; never assume a raw registry view stays valid across arbitrary removals.
