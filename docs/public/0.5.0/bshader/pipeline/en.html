Shader assets and compilation

Source, shader package, and material instance are separate assets with different responsibilities.

Files and extensions

ExtensionPurpose
.bshader / .shadBshader source; both supported.
.matLower-level Filament material source.
.matinstMaterial instance: shader UUID and parameter values.
.filamatBinary package compiled by Filament matc.
.metaAsset identity/import metadata; preserve it when moving assets.

Put sources inside the project's Assets directory. The editor's New Shader action creates a .shad source. A .bshader source added to Assets works through the same pipeline. Do not rename a .matinst to a shader extension or assign a shader where a material picker is required.

Editor workflow

  1. Create or copy your source into Assets and let the Asset Browser register it.
  2. Create a Material asset in the Asset Browser. Select it and assign your shader to its Shader field.
  3. Set the reflected parameter fields. Assign texture properties using project image assets.
  4. Assign that material to a Mesh or Primitive Object's Material Asset field.
  5. Check Console for translation or Filament compiler errors if the surface does not appear.

There is no separate public engine-init or shader-build command to run. Inspecting an unused shader reflects its parameters but does not compile it for the GPU. Preparing a referenced material invokes compilation on demand; the editor reuses successful cached packages until the translated source or compiler changes. The shipped editor needs its Bshader translator and Filament matc tool.

What the pipeline does

  1. The asset database imports source and tracks UUID/cache paths.
  2. Bshader parses declarations, validates names/control flow/defaults, and expands high-level calls.
  3. The translator emits Filament source with editor-only defaults. Ordinary properties use the parameter struct; samplers use separate uniforms.
  4. Editor/materials.py extracts typed reflection and strips defaults. Compatibility lowering remains for older flat references.
  5. Filament matc --platform desktop --api all validates GPU types/stages and builds a binary package.
  6. The renderer loads the package, creates material instances, binds textures, and uploads parameter values.

Given the asset's cache path, the editor writes <cache>.reflection.json, <cache>.translated.mat, <cache>.filamat, and <cache>.build.json. These are generated data, not authoring files. Rebuilding can replace them. Compiler failures do not publish a new package. Windows compiler input is staged through ASCII-safe temporary paths so Unicode project paths do not become tool arguments.

Reflection, defaults, and updates

Property declarations become typed Properties fields and shader reflection. A .matinst stores parameter overrides keyed by name. A missing override uses the reflected default; an undeclared default uses the type's fallback. Set explicit defaults for predictable results. Textures store asset UUIDs, not operating-system paths. Floats must be finite, integers signed 32-bit, vector/matrix values correctly sized, booleans actual booleans, and texture references valid assets.

At runtime the material service resolves these values and the renderer sets corresponding Filament material-instance parameters. Changing a compatible parameter does not rebuild the shader or add a uniform. Changing shader declarations requires reflection/recompilation. Shared materials affect all users; instantiate a copy for one object's independent changes.

C++ and Lua boundary

Use Shader::Load, Material::Create/Load/Instantiate, typed setters such as SetFloat, SetVec4, SetMatrix4, and SetTexture, then ApplyTo. Lua exposes the matching material API. See runtime materials for ownership and complete examples. These APIs operate on existing shaders, not arbitrary shader source. Keep the translator/compiler in authoring tools, not the gameplay loop.

Vertex processing

Without a vertex block, Filament supplies its standard geometry path. With one, Bshader generates materialVertex to modify position/normal/UV/color before final projection. Skinning, mesh attribute handling, and standard rendering remain Filament responsibilities. CPU picking and bounds do not automatically follow shader deformation.
