Write a Lua behavior

Lua behaviors let you add gameplay without compiling a native C++ module. Their source files are project assets.

Create the script

If variables, tables, self, or the difference between dots and colons are new, read Lua terms and first calls first. It explains each part of the notation used below.

Create a Lua Behavior in the Asset Browser, or add Assets/Scripts/Walk.lua. Use this complete example:

-- COMPONENT(Walk)
-- PROPERTY(float, Speed, 4.0)
local B = Bazzalt
local Walk = { Speed = 4.0 }

function Walk:OnUpdate(deltaTime)
    local direction = B.Vec3.new(B.Input.GetAxis(B.InputAxis.Horizontal), 0,
                                -B.Input.GetAxis(B.InputAxis.Vertical))
    if direction:LengthSquared() > 0 then
        local transform = self.Entity:GetWorldTransform()
        transform.Position = transform.Position + direction:Normalized() * self.Speed * deltaTime
        self.Entity:SetWorldTransform(transform)
    end
end

return Walk

The script returns a behavior table. The editor reads COMPONENT and PROPERTY declaration comments to discover its name and Inspector fields; those comments are not Lua functions. The runtime supplies self.Entity and applies Inspector property values before calling OnCreate.

Direction is normalized so diagonal movement is not faster. Multiplying by deltaTime gives movement per second rather than per frame. The example moves in world X/Z directions, not relative to the game camera, and does not implement collision or gravity.

Attach and test

  1. Select an entity with a Primitive Object or model so movement is visible.
  2. Attach Walk through Add Component or drag the Lua script onto the entity.
  3. Set Speed if needed, then press Play.
  4. Click Game output for input focus and use WASD.

Name the behavior uniquely across both Lua and C++ scripts. If you already created COMPONENT(Walk) in C++, choose a different name for this example. Duplicate component names or property names are rejected, not combined into one component.

What happens before Play

The Lua importer parses the source and stores VM bytecode in the asset cache. The runtime executes that imported bytecode. Lua-only Play does not invoke a C++ compiler; syntax errors still prevent a valid import. Read Console if the script cannot be imported or executed.

Changes to attached Lua files are imported before Play. Changes made while playing are deferred until Stop rather than replacing the behavior halfway through a callback. Each attachment has isolated Lua state. Do not use a Lua global as shared persistent storage across entities.

Lifecycle callbacks

  • OnCreate(): initialize the attachment's runtime state.
  • OnUpdate(deltaTime): per-frame gameplay.
  • OnFixedUpdate(fixedDeltaTime): fixed-step gameplay.
  • OnDestroy(): release state you own.

Methods are optional. Disable an attachment to stop its updates without removing the authored properties. Runtime state is discarded on Stop.

Available libraries and limits

Gameplay uses the Bazzalt API, not direct engine initialization or operating-system access. The runtime intentionally omits facilities such as os, io, package, debug, and loadfile. It also bounds script memory and execution so a runaway loop is reported instead of deliberately holding the editor forever. Do not treat these limits as permission to run arbitrary untrusted bytecode.

Continue with Lua API conventions before editing components directly. Lua's copied-component model differs from a C++ component reference.
