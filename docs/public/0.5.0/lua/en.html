Write a Lua behavior

Lua behaviors let you add gameplay without compiling a native C++ module. Their source files are project assets.

Create the script

If variables, tables, self, or the difference between dots and colons are new, read Lua terms and first calls first. It explains each part of the notation used below.

Create a Lua Behavior in the Asset Browser, or add Assets/Scripts/Walk.lua. Use this complete example:

local B = Bazzalt
local Walk = COMPONENT("Walk")
Walk.Speed = PROPERTY("float", 4.0)

function Walk:OnUpdate(deltaTime)
    local direction = B.Vec3.new(B.Input.GetAxis(B.InputAxis.Horizontal), 0,
                                -B.Input.GetAxis(B.InputAxis.Vertical))
    if direction:LengthSquared() > 0 then
        local transform = self.Entity:GetWorldTransform()
        transform.Position = transform.Position + direction:Normalized() * self.Speed * deltaTime
        self.Entity:SetWorldTransform(transform)
    end
end

return Walk

COMPONENT("Walk") creates the behavior table. PROPERTY("float", 4.0) returns its default value and declares Speed for Properties. These are real global Lua functions supplied during source initialization. Return the same table. The editor reads declarations without executing your code; the runtime supplies self.Entity and applies inspector overrides before OnCreate.

Component and property declarations

Use one local Name = COMPONENT("UniqueTypeName") declaration, followed by Name.Field = PROPERTY("type", default). Component names must be unique across C++ and Lua; field names cannot repeat. Keep declarations unconditional and at top level. The filename may differ from the declared component name.

Supported types are float, double, int, bool, string (or std::string), Vec2, Vec3, Vec4, and Quaternion. Scalars require literal defaults. Vectors and quaternions require explicit literal coordinates, for example Walk.Direction = PROPERTY("Vec3", B.Vec3.new(1, 0, 0)). Use B or Bazzalt as the constructor prefix. Dynamic expressions are not inspector declarations. Declaration helpers are not gameplay APIs and should not be called from lifecycle methods.

Existing comment-based COMPONENT/PROPERTY metadata and plain returned tables remain supported for older scripts. New templates use functions; when functions are present, comment metadata is ignored. Lua source is still imported into bytecode; there is no C++ compilation step.

Inspector-only field rules

Pass a third literal options table to PROPERTY. These rules control authoring in Properties only: they do not constrain Lua assignments, runtime overrides, or gameplay. Changing a controlling field updates other fields immediately without changing selection. A rejected edit restores the saved value and shows a validation tooltip; invalid older values are shown with a warning rather than silently rewritten.

Walk.UseLimit = PROPERTY("bool", true)
Walk.Limit = PROPERTY("float", 10.0, { Min = 0, Max = 100 })
Walk.Speed = PROPERTY("float", 4.0, {
    Min = 0, Max = 100, Step = 0.5,
    EnabledIf = "self.UseLimit",
    Validate = "not self.UseLimit or value <= self.Limit",
    Message = "Speed must not exceed Limit",
    Tooltip = "Movement speed in units per second"
})
Walk.Label = PROPERTY("string", "Player", {
    MinLength = 1, MaxLength = 24, Trim = true, Filter = "Identifier",
    VisibleIf = "self.UseLimit"
})

Numeric and vector fields accept Min, Max and Step (applied per vector coordinate). Integer bounds and steps must be integers. String fields accept MinLength, MaxLength (0–4096), Trim, Filter, and Pattern. Filter may be Digits, Letters, Alphanumeric or Identifier. Pattern is a case-sensitive glob, such as player_*, not a regular expression. Use MinLength = 1 when empty text must be rejected.

Any field may use ReadOnly, VisibleIf, EnabledIf, Validate, Message, Tooltip and Label. Label changes its display caption, not its serialized field name. VisibleIf hides both the label and input; EnabledIf and ReadOnly keep the value visible but non-editable. Conditions must reference existing inspector properties.

Custom logic uses bounded expression strings, not Lua callbacks. Read another property with self.Field and the proposed edited value with value. Supported operators: and/or/not, ==, ~= (or !=), comparisons, +, -, *, / and %. Supported helpers: Len, Contains, StartsWith, EndsWith, Matches (glob), Abs, Min and Max. Example: Validate = "StartsWith(value, 'player_') and Len(value) > 7". Boolean literals true and false work. Imports, arbitrary function calls, indexing and unrestricted code execution are forbidden. Rules never run project Lua during inspection.

Direction is normalized so diagonal movement is not faster. Multiplying by deltaTime gives movement per second rather than per frame. The example moves in world X/Z directions, not relative to the game camera, and does not implement collision or gravity.

Attach and test

  1. Select an entity with a Primitive Object or model so movement is visible.
  2. Attach Walk through Add Component or drag the Lua script onto the entity.
  3. Set Speed if needed, then press Play.
  4. Click Game output for input focus and use WASD.

Name the behavior uniquely across both Lua and C++ scripts. If you already created COMPONENT(Walk) in C++, choose a different name for this example. Duplicate component names or property names are rejected, not combined into one component.

What happens before Play

The Lua importer parses the source and stores VM bytecode in the asset cache. The runtime executes that imported bytecode. Lua-only Play does not invoke a C++ compiler; syntax errors still prevent a valid import. Read Console if the script cannot be imported or executed.

Changes to attached Lua files are imported before Play. Changes made while playing are deferred until Stop rather than replacing the behavior halfway through a callback. Each attachment has isolated Lua state. Do not use a Lua global as shared persistent storage across entities.

Lifecycle callbacks

  • OnCreate(): initialize the attachment's runtime state.
  • OnUpdate(deltaTime): per-frame gameplay.
  • OnFixedUpdate(fixedDeltaTime): fixed-step gameplay.
  • OnDestroy(): release state you own.

Methods are optional. Disable an attachment to stop its updates without removing the authored properties. Runtime state is discarded on Stop.

Available libraries and limits

Gameplay uses the Bazzalt API, not direct engine initialization or operating-system access. The runtime intentionally omits facilities such as os, io, package, debug, and loadfile. It also bounds script memory and execution so a runaway loop is reported instead of deliberately holding the editor forever. Do not treat these limits as permission to run arbitrary untrusted bytecode.

Continue with Lua API conventions before editing components directly. Lua's copied-component model differs from a C++ component reference.
