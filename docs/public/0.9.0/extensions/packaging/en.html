Package builds and game deployment

Build > Build Package opens a modal authoring window. Select a YAML manifest, review its sections, edit scalar values in the field tree, or use Advanced Manifest to edit structured lists and mappings. Edit strings as plain text, use true/false for booleans, and enter finite numbers in numeric fields. Build saves the validated authoring manifest.

Build a .bpack

Select a prebuilt runtime SDK, host platform/target architecture and optional C++ compiler path. Build Package uses a blocking progress child window while work runs in a worker thread. Cancel takes effect between files and compilation steps. A completed package replaces the destination atomically; failures keep its previous contents.

python -m Compiler.extensions --manifest extension.yaml --output StudioMath.bpack --runtime path/to/runtime --platform windows --architecture x64

Lua scripts are compiled to Lua 5.4.9 bytecode. Native functions and C++ behaviors are compiled with the public ScriptSDK; public headers and necessary source are retained in the package for project compilation and other supported architectures. Registered editor resources remain in the package but are not game runtime content.

Installation and activation

Window > Extensions imports .bpack files into the editor-wide application-data store. New imports are disabled. Enable dependencies first, then enable the extension and restart the editor. Disable an extension before replacing its active version. Another editor cannot write the registry simultaneously. Old content-addressed package versions remain available for existing project pins.

Use Enabled SDKs in Project writes Extensions.lock.json for the active project. It pins IDs, versions and package digests. Reopen the project to materialize registered components and refresh SDK deployment. A copied project must install the exact packages in its lock before building; enabled editor-wide versions never silently replace project pins.

Standalone game output

Game compilation resolves pinned packages, validates compatibility and stages runtime modules under the cooked project's ext directory. Public SDK modules and private Runtime helpers are included; Editor-scoped scripts and panel/menu resources are excluded. Registered component behaviors are cooked through the ordinary project script pipeline. SDK headers, C++ source, Lua source, Python and editor UI files are not copied into the final game runtime content.

The ext runtime data participates in the existing packaging, encryption and signed inventory pipeline. With package output, ext is a logical directory inside protected game content and is available in the player's verified extraction directory. Native libraries must be available as decoded files when the OS loads them; encryption does not mean the OS executes encrypted bytes. Game execution does not read the editor's extension store.

Limits and trust

Version 1 limits a package to 512 MiB unpacked, 64 MiB per file and 8192 payload files. Manifests are bounded, keys must be unique, and non-finite/recursive YAML values are rejected. Extraction rejects absolute paths, traversal, case-insensitive collisions, symlinks and encrypted ZIP members. SHA-256 inventory checks detect corruption; they are not publisher signatures. Enable only native packages whose authors you trust. Lua controllers have instruction and VM memory limits and no standard filesystem/process libraries.
