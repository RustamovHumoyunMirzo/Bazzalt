Version control with Git

Git keeps a history of your project files and lets a team combine changes. Open Window > Version Control inside an active project. The dialog shows the repository folder, current branch, upstream branch and the number of commits ahead or behind it. Its three tabs contain changes, commit history and local branches.

Set up a project repository

Install Git 2.23 or later and make its executable available on PATH before starting the editor. Bazzalt uses your installed Git and its repository configuration. Configure your commit identity with git config --global user.name "Your Name" and git config --global user.email "you@example.com". A repository-local identity also works.

If your project already belongs to a repository, the dialog discovers its root. A project in a subfolder uses the containing repository, so its status, commits, stashes and branch operations cover that entire repository. Check the folder displayed at the top.

For a new project, choose Initialize Git and confirm. This creates a local repository and adds ignores for /.bazzalt/Cache/, /.bazzalt/Editor/ and /bin/. Initialization appends missing patterns to .gitignore. Source assets, scripts, scenes, project configuration and asset .meta files belong in version control. Metadata stores persistent asset IDs, which keep scene and material references connected across machines.

Working files, staged files and commits

The working tree contains the files currently on disk. The index, also called the staging area, holds the exact versions prepared for the next commit. A commit records that staged snapshot with your identity and a message. Unsaved scene edits remain in editor memory until you save them.

  1. Save the scenes and documents you intend to share.
  2. Select files in Changes. Use Ctrl or Shift to select several rows.
  3. Choose Working Tree or Staged above the diff to compare the selected file. A new untracked text file displays its contents.
  4. Choose Stage Selected. Asset files and their metadata are staged together. For an unstaged rename, select both the deleted and new rows. Git detects the rename after both sides are staged. Unstaging a detected rename includes its original path.
  5. Enter a message explaining the change, then choose Commit Staged.

The status columns use Git codes. M means modified, A added, D deleted, R renamed, C copied, U conflicted, ? untracked and . unchanged. A file can contain both staged and unstaged edits. Hover over a status column heading for the legend.

Unstage Selected updates the staging area for the next commit. Discard Working Changes asks for confirmation and restores selected tracked files, including metadata, to their staged versions. Discard requires tracked files. The row context menu provides staging, unstaging, resolution and discard actions.

Inspect history and diffs

History lists the latest 100 commits with ID, author, date and subject. Select a commit to inspect its full message and patch. This view includes the commit's repository-wide changes. Git binary-file notices appear for assets without a text diff. Preview text is capped at 2 MiB and displays a truncation notice when that limit is reached.

Branches and stashes

A branch names a line of development. Select a local branch in Branches and choose Switch Branch, or use Create Branch to start another branch from the current commit. Switching requires a clean repository and a target branch containing this project file. Changes across the repository must first be committed or stashed.

Stash Changes temporarily stores tracked and untracked changes and cleans the worktree. Git ignore rules determine which untracked files the stash collects. Apply Last Stash restores the latest stash. A successful application removes that stash. A conflicted application keeps it available in Git.

Stop Play and save scene changes before operations that rewrite working files. Open asset documents flush their changes before the operation. The editor pauses updates and releases scene-file locks for the Git write. It then reloads project assets and surviving loaded scenes, restores the active scene when available, and clears undo history and open graph/mixer document buffers from the previous revision.

Merge and resolve conflicts

Merge Branch combines a selected local branch into the current branch. If both branches changed the same area, Git may create a conflict. Conflicted rows use the theme's error color. Editing stays paused while these conflicts remain, so invalid scene files stay out of the runtime.

  1. Select a conflicted UTF-8 text file and choose Resolve Conflict, or double-click its row.
  2. Inspect Base · Index Stage 1, Ours · Index Stage 2 and Theirs · Index Stage 3.
  3. Edit the Resolution tab. Remove conflict markers and preserve the file's required format.
  4. Choose Save and Stage Resolution. Repeat for every conflicted file, including metadata.
  5. Once all conflicts are staged, the editor reloads the project. Enter a merge commit message and choose Commit Staged.

Text resolution supports regular UTF-8 files up to 2 MiB. For binary assets, large files, symlinks or delete/modify conflicts, use an index-stage button to select a complete version. Selecting an absent stage deletes the file. These choices require confirmation. During a rebase, Git's stage 2 and stage 3 refer to the rebased upstream and replayed commit respectively, so inspect their contents before choosing.

Abort Merge confirms and restores the pre-merge state. Git worktrees and repository operation markers are detected through Git itself, including repositories whose .git entry is a file. An existing rebase can be resolved and staged here, then continued or aborted with Git's command line. The branch tools reject a second operation while a merge or rebase is in progress.

If a resolved project cannot load, restore valid project/scene files and choose Retry Project Reload. The editor keeps updates paused until loading succeeds. Closing the editor also releases the pending session.

Share with a remote

Configure remotes and upstream tracking with Git, for example git remote add origin URL and git push --set-upstream origin BRANCH. Set up your Git credential manager or SSH agent. The editor uses existing credentials and shows authentication failures in its status area.

Fetch updates remote references. Pull (fast-forward) advances a clean branch when its upstream is ahead. Diverged branches require an explicit merge. Push publishes through the current branch's configured upstream. Remote actions run when clicked.

Refresh and operational limits

The visible dialog refreshes status every five seconds and supports manual refresh. Git runs on a dedicated worker with one operation at a time. File selection, diff rendering and commit-message editing stay on the Qt UI thread. Commands have a 60-second deadline, and status/history output has a 16 MiB limit. An operation that times out reports an error. Inspect repository status before retrying.

Git executes configured hooks and asset filters during mutation commands and uses its signing configuration for commits. Text previews disable external diff programs and text-conversion helpers. Filenames pass as literal path arguments, including spaces, Unicode and pattern characters. Git and this dialog are editor tools. The Git dialog runs in the editor process.
