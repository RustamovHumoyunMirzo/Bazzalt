AI behavior trees and blackboards

Author NPC logic as a .bbtree asset using the built-in block workspace or XML. Each Behavior Tree Agent owns its execution state and typed blackboard. Trees run on fixed gameplay updates before Jolt simulation, and work in packaged desktop and Android games.

Create and run an NPC

  1. In the asset browser, choose Create → Behavior Tree. Double-click the .bbtree asset.
  2. Drag behaviors from the searchable toolbox. Put children inside composite/decorator mouths and connect siblings in execution order. Keep exactly one connected root. Composites need at least one child; decorators need exactly one.
  3. Choose Save. Incomplete or invalid graphs show an error and do not replace the last valid file. Undo/Redo and clipboard actions use the editor's focused-document routing, as shader graphs do.
  4. Add Behavior Tree Agent to the NPC and select the Tree asset. Enable Loop to restart the tree on the next fixed tick after Success or Failure. Disable Loop for one completion.
  5. For physics actions add a dynamic Rigidbody and a collider. Enter Play. Missing bodies or unavailable custom handlers cause Failure, allowing selectors to choose fallback behaviors.

Block names, category names, field labels, search and descriptions use the editor locale catalog. Node identifiers and XML attribute names are stable and never translated. Block comments, collapsed state and layout survive editor saves.

XML and Unlock

While blocks own a document, the XML tab is a read-only generated view. Unlock XML switches the same .bbtree file to source authoring with locked="false" and makes blocks read-only. Unlock itself is undoable. Write XML directly in the source tab or an external editor. Reload from disk explicitly discards local edits; saving refuses to overwrite a file changed externally. To import a source file as editable blocks, set locked="true" externally and reopen it. XML edits cannot silently switch ownership during an editing session.

<BehaviorTree version="1" locked="false">
  <Blackboard>
    <Vector key="target" x="10" y="1" z="0"/>
    <Number key="investigate" value="0.8"/>
    <Number key="idle" value="0.2"/>
  </Blackboard>
  <Tree>
    <Utility>
      <Option key="investigate" weight="1">
        <MoveTo key="target" speed="3" radius="0.3"/>
      </Option>
      <Option key="idle" weight="1"><Wait seconds="2"/></Option>
    </Utility>
  </Tree>
</BehaviorTree>

The document needs version="1", one Tree section and one behavior root. Blackboard is optional. locked defaults to true. Optional authoring attributes id, editor-x, editor-y, comment, comment-open and collapsed do not affect execution. Numeric fields must be finite; time, distance, speed, radius and repeat count cannot be negative. XML is limited to 1 MiB, 4096 behavior nodes and 64 behavior levels. DTDs, external entities, unknown behavior tags and invalid child counts are rejected. Custom behavior uses named Action and Condition nodes, never executable XML.

Blackboard values

Keys are case-sensitive strings. Supported values are Bool, Number (double), String and Vector (Vec3). Defaults initialize missing keys without replacing gameplay values. Write defaults in Blackboard using key and value attributes for Bool/Number/String, and x/y/z for Vector. Booleans are true/false. Keys must be unique. Set nodes can also establish values in a block-authored tree. Memory is independent for every NPC, even when several NPCs reference the same asset. Reset clears execution progress and cooldowns, but preserves blackboard values.

Execution and utility AI

Every behavior returns Success, Failure or Running. Sequence and Selector remember a running child. Reactive variants reevaluate priorities from the first child each tick and cancel a preempted running branch. Parallel does not retick completed children while waiting; failure cancels remaining running children. Terminal trees reset traversal state; Loop determines whether the agent starts again. Disabled agents cancel their running work. Script stop/reload disconnects Lua handlers before closing their VM.

Utility reevaluates each Option score every tick: numeric blackboard value × weight. A missing/nonnumeric score is zero. The greatest score wins, first on ties; negative scores are valid. A new winner cancels the previous branch. Utility selects among already computed scores: calculate needs, distances, visibility or combat priorities in gameplay handlers or blackboard actions. Repeat performs at most one child completion per tick, count=0 succeeds immediately, and child Failure ends repetition. Timeout=0 fails before ticking its child. Wait=0 succeeds immediately. Cooldowns advance on fixed ticks even while their branch is not selected; explicit Reset clears them.

Jolt actions and movement

Physics actions use the scene's PhysicsScene facade. SetVelocity, ApplyForce and ApplyImpulse use world-space vectors. Stop sets linear velocity to zero; Wake and Sleep change body activation. Raycast starts at the NPC world position and excludes its own body; it stores a hit boolean at key and a point vector at key + ".point" (the point is erased on a miss). OverlapSphere stores a numeric hit count, excludes self and returns Success for nonzero results. Queries use the default physics layer mask and exclude triggers.

MoveTo reads a world-space Vec3 from the blackboard, sets a dynamic body's velocity toward it, and remains Running until within radius. It stops velocity on arrival or cancellation. It is direct steering, without obstacle avoidance or navmesh pathfinding. For paths around obstacles, use Navigation/NavigationAgent from a named gameplay Action and return Running until arrival. WithinDistance checks the same target without moving.

Compiler, dependencies and packaged games

The asset importer validates .bbtree sources and preserves their UUID metadata. The desktop and Android compiler validates every .bbtree again, writes a runtime XML cache with authoring layout/comments removed, and packages the source/cache under the same asset identity. Scene/prefab BehaviorTreeAgent.Tree references retain the tree transitively. Known asset identities or asset paths in XML attributes are retained during content filtering; excluding a required dependency fails the build. Assets loaded only from custom gameplay code must be included explicitly in packaging rules. No editor Python or Qt code is needed by the game runtime.

C++ and Lua

Both languages support standalone trees, typed blackboards, agent components and custom actions/conditions. Use the C++ guide or Lua guide for signatures, examples, handler ownership and cancellation. The API reference pages are generated from public headers and actual Lua bindings.

Behavior parsing, tree execution, utility selection and per-agent runtime state live in the same bazzalt_ai.dll module as navigation (libbazzalt_ai.so on Linux/Android, libbazzalt_ai.dylib on macOS). The core engine keeps the public API and Lua bindings and forwards through a versioned private module table. Ship the matching AI module beside the core runtime; existing runtime staging includes it.
