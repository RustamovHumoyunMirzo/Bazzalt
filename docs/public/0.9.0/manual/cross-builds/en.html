Cross-platform game builds

A game build cooks your project content and combines it with a prebuilt runtime for the target machine. It never builds the engine. The target platform and architecture describe the game, while the host is the machine running the editor/compiler. Keep these separate when choosing tools.

These methods do not install Zig, MinGW, WSL, compilers, sysroots or SDKs for you. The editor detects installed executables through PATH; Detect installed toolchain fills the profile when possible. Browse selects a local executable or SDK/sysroot folder using the platform's native file dialog. ARM64 runtime SDKs are built and tested on dedicated native CI runners and distributed separately from the x64 editor.

Choose a build method

  1. Open Build > Build Settings and select the game's target platform.
  2. Expand that platform's container. Select its architecture and runtime SDK. Separately installed matching Core SDKs are detected automatically.
  3. Choose Native, Local WSL, Zig, MinGW-w64 or Content / Lua only. Automatic uses native builds for native targets and detects available cross tools for foreign targets.
  4. Use Detect installed toolchain, or Browse to select an executable. Set a sysroot only when your toolchain requires a target header/library tree.
  5. Build the project. Cross output is verified offline when it cannot run on the host. Test the result on the target OS before distributing it.

Windowing, production metadata, packaging and intro settings stay shared. Each platform retains its own architecture, backend, build method, toolchain, sysroot and key-delivery options.

Why a matching C++ SDK matters

An ABI is the binary contract between compiled libraries: symbol names, calling conventions, object layouts and standard-library types. BAZZALT exposes C++ values such as strings across its SDK boundary. A MinGW or Zig compiler cannot safely link to an arbitrary MSVC-built core just because both files target Windows x64. The compiler rejects that combination instead of producing a game that fails later.

A cross-SDK provider must build and test the engine/runtime with the intended toolchain, stage all its runtime DLLs/shared libraries, and declare the exact compiler contract in runtime.json. Game builds consume that SDK; they do not rebuild it. This is an SDK-provider task, not a requirement for ordinary native game builds. Shipped native SDKs do not automatically become GNU/Zig SDKs.

"cross_toolchain": {
  "method": "zig",
  "version": "0.14.1",
  "triple": "x86_64-windows-gnu"
}

The version above is an example. Use the exact output of zig version, or the MinGW compiler's -dumpfullversion. Supported triple CPUs are x86_64, i686 and aarch64. MinGW uses a -w64-mingw32 suffix; Zig uses -windows-gnu or -linux-gnu. A sysroot does not repair a C++ ABI mismatch.

Projects without native C++ compilation

Content / Lua only combines cooked assets, Lua bytecode and an existing target runtime without invoking a C++ cross compiler. It can therefore use a shipped native target SDK from another OS. Attached C++ behaviors, C++ global subsystems and extension modules that need source compilation are rejected in this mode. Precompiled compatible target extension modules remain usable. Choose a native remote worker for C++ projects when you have only the standard shipped SDK.

Windows to Linux with WSL

Install and initialize a Linux distribution in WSL, then install the Linux BazzaltCompiler, matching Core SDK, and Clang development tools there. Leave WSL distribution blank to use the default. The compiler is detected through the distribution's PATH; optional WSL compiler and runtime fields refer to Linux paths inside that distribution.

The project remains on the Windows filesystem and is mapped with wslpath. Cancellation is forwarded to the Linux compiler; completed output paths are mapped back for the editor. This path uses the normal Linux SDK and supports C++ without mixing a Windows SDK into a Linux link. Worker environment keys must be provisioned in WSL when using environment-based encryption.

Verification and launch

Native builds run the packaged player's verification mode. Foreign binaries receive P-256 signed-inventory verification, executable/seal hashing, encrypted-manifest authentication, signed-file checks and unexpected-file rejection without executing target code on the host. Portable Zstandard packages are readable by all supported players. Windows version resources are updated with LIEF on non-Windows hosts.

Build and Launch requires an executable target compatible with the host. A foreign game must be copied to its target machine. Offline verification checks package integrity; it cannot replace a target-device rendering/gameplay test. macOS bundles require native code signing on a Mac, so use a Mac worker from Windows/Linux. Account-scoped Windows DPAPI keys are unsuitable for distribution from another machine or worker account; choose portable key delivery.

Architecture limits

ARM64 is the supported ARM target. ARM32, IA64, PowerPC and other legacy architectures do not have runtime SDKs. Modern macOS cannot run 32-bit applications: Apple removed that runtime in macOS Catalina 10.15. BAZZALT targets macOS 12 or newer and rejects x86 macOS output. It does not advertise a nonfunctional 32-bit option.
