Developer console and CVars in C++

Register from C++

#include <Bazzalt/DeveloperConsole.h>
#include <Bazzalt/CVar.h>
// Inside a subsystem or script lifecycle callback on the engine thread:
Bazzalt::DeveloperConsole::SetEnabled(true); // opt in for standalone development
Bazzalt::CVarDefinition speed;
speed.Name = "game.speed";
speed.Description = "Movement speed in metres per second";
speed.DefaultValue = 4.0; // double; use std::int64_t(...) for integer CVars
speed.Minimum = 0; speed.Maximum = 30;
speed.Flags = Bazzalt::CVarFlags::Archive;
Bazzalt::CVar::Register(speed);
const double value = std::get<double>(Bazzalt::CVar::GetValue("game.speed"));
auto handle = Bazzalt::DeveloperConsole::RegisterCommand(
    {"game.ping", "Check command dispatch", "game.ping", false},
    [](const std::vector<std::string>& args) {
        if (!args.empty()) throw std::invalid_argument("game.ping takes no arguments");
        return std::string("pong");
    });
auto result = Bazzalt::DeveloperConsole::Execute("game.speed 6.5");
if (!result.Success) { /* result.Output explains rejection */ }
Bazzalt::DeveloperConsole::Log("A runtime message");

CVar.GetInfo returns a copy containing Definition, Type, Value and optional PendingValue; GetAll returns sorted copies, optionally filtered by prefix. Unregister removes a variable; UnregisterCommand removes a command by handle. Complete accepts command prefixes and CVar-name arguments such as "set game.sp". GetHistory/ClearHistory manage command recall. Message queries accept ConsoleFilter by level, exact source and text substring. Clear also clears matching mirrored editor messages.

Commands and CVars

A command performs an action. A console variable (CVar) stores a named, typed setting that code can read and tune. Names are process-wide, case-insensitive ASCII letters, numbers, dot, dash and underscore; a name cannot start with a number. Duplicate command/CVar names are rejected, including collisions with built-in commands. Register shared names once, normally in a global subsystem after the services it uses are ready.

DeveloperConsole works in standalone games. The existing Console API remains editor-only logging. DeveloperConsole.Log writes a bounded runtime store and mirrors output to the editor when present. The developer console is enabled in the editor, but standalone games must explicitly enable it from trusted startup code. Enabled state does not pause simulation. Showing its overlay captures gameplay input for that tick; closing keys are consumed too. Its GUI scene is private and is never saved into game scenes.

Built-in commands

SyntaxBehavior
help [name]Syntax and descriptions.
commands [prefix], cvars [prefix]List registered names/settings.
get name, nameRead a CVar.
set name value, name valueWrite a typed value.
reset name, toggle nameRestore default, or invert a Boolean.
echo text, clear, historyWrite output, clear messages, list entered commands.
app.quit [exitCode]Request normal shutdown, exit code 0–255.

Use quotes for a value containing spaces, or an empty string: set game.title "Two words", set game.title "". Escaped quotes/backslashes are supported. This is not a shell: no process execution, environment expansion, command chaining or script-file execution. Semicolons in arguments remain text. Lines are limited to 4096 bytes and 64 arguments. Exceptions become failed ConsoleResult values and error messages. Custom C++ handlers must return promptly; schedule expensive work through Jobs.

Types, flags and change events

DefaultValue fixes a CVar’s Boolean, signed 64-bit integer, double or string type. C++ writes must match exactly. Lua integers can be written to float CVars without making common numeric literals awkward; fractional numbers cannot be written to integer CVars. Numeric Minimum/Maximum are inclusive; invalid, out-of-range and nonfinite values are rejected. Strings have a 4096-byte budget. SetFromString uses locale-independent parsing and rejects trailing junk.

FlagEffect
ReadOnlyWrites, reset, toggle and configuration import are rejected.
ArchiveIncluded by ExportArchive; only archived CVars may be imported.
CheatRequires host SetCheatsAllowed(true); disabled by default. Disabling cheats restores cheat CVars to defaults and discards their pending changes.
RestartRequiredWrites update PendingValue while the effective Value stays unchanged. The host applies pending changes at a safe restart boundary.

Registration accepts an optional change callback; Subscribe observes changes globally. CVarChange contains Name, Previous, Value and Pending. Repeating an unchanged value does not notify. Callback exceptions are logged after the change commits. Recursion is limited to 16 levels. ApplyPendingChanges commits latched values and sends effective-value events; it does not restart the process or recreate a renderer automatically.

Engine tunables

app.target_fps and app.background_fps accept 0–1000; zero is uncapped. app.run_in_background is Boolean. Writes call the real Application controls. Frame-rate and background scheduling policies are honored by the standalone player; the editor retains its own UI tick cadence. time.scale is a cheat-protected 0–100 float and updates the real gameplay clock. debug.stats displays live FPS/frame count in the open runtime console. These tunables apply when their CVar changes; direct calls to the separate Application/Time APIs do not automatically rewrite the stored CVar value.

Configuration and lifetime

ExportArchive returns a name-to-text map including pending restart values. Persist that map in your game’s configuration or SaveGame slot; the console does not choose a file path, execute configuration text or store secrets. ImportArchive validates every name, type, flag and bound before publishing changes; callbacks run after all values are committed. Unknown names reject the import, so register your variables first and migrate old configuration keys explicitly.

Commands, variable callbacks and subscriptions inherit the registering native module or Lua VM owner. They disconnect when scripts stop/unload; native code stays leased while callbacks execute. Compatible CVar values survive owner teardown until re-registration in the same application, within a bounded 4096-entry recovery store. Register callbacks from lifecycle methods, not unowned static storage. During hot reload, register again in OnReload as well as OnCreate: the old VM’s functions are never reused. Avoid storing callback functions or CVarDefinition userdata in reload state; keep descriptors local and transfer ordinary data.

Registration, variable access and command execution belong on the engine thread. Log, GetMessages and Clear support worker threads. Limits: 4096 CVars, 4096 custom commands and 4096 change listeners. History defaults to 256 lines (0–4096 configurable); output defaults to 2048 messages (1–65536 configurable), with an additional fixed 8 MiB text/source byte budget. Oldest messages are evicted when either budget is reached. Handles are monotonic; removing an old command handle cannot remove a later registration. SetEnabled(false) hides the overlay and rejects Execute, but trusted gameplay can still read/write CVars. Cheat flags and disabled state are development controls, not a multiplayer authority/security boundary.
