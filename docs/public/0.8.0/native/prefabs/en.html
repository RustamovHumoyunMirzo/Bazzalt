C++ prefab assets

A prefab is a reusable entity hierarchy stored in a YAML .bprefab asset. Each instance receives its own entity UUIDs and components. Meshes, materials, audio and other referenced assets stay shared.

Create and place a prefab

  1. Build an object and its children in Hierarchy. Add the components and scripts you want to reuse.
  2. Drag its Hierarchy row into an Asset Browser directory, or choose Prefab → Create Prefab from Selection in its context menu.
  3. The asset is created with .meta identity. Its original hierarchy becomes a linked instance, shown with a blue prefab icon.
  4. Double-click the prefab asset to instantiate it in the active scene, or drag it onto a Hierarchy parent or scene header. Instances in inactive scenes remain editable without changing the active viewport.

Editing an instance does not immediately edit the source asset. The Prefab inspector section shows its source and whether it has overrides.

Overrides and source updates

Change a component property, name, hierarchy, or add/remove an object. These changes become instance overrides. Root placement is instance-specific: moving, rotating or scaling the instance root is preserved when updating or reverting and does not mark it overridden.

  • Apply Overrides to Asset: writes this instance into its source prefab, preserving the .meta UUID. Other loaded instances update using a three-way merge that keeps their own overrides.
  • Revert Overrides: restores the latest source hierarchy and components while retaining the root placement and stable UUIDs of surviving source objects.
  • Update from Asset: merges the latest imported source with this instance's overrides. Use this after editing the YAML source externally.
  • Unpack Prefab: removes the source link while keeping all current entities and components.

Prefab edits support scene and asset-file undo/redo. Commands snapshot every loaded scene, so applying across scenes can be undone together. The existing editor undo file-size and memory limits still apply. Source files edited externally are protected from being overwritten by an outdated undo command.

Identity, references and missing assets

Source-local entity IDs are remapped when instantiated. Built-in joints, vehicle wheel references, LOD roots, camera-bound GUI references and typed script entity references point to the new instance. Asset UUIDs keep referring to shared assets. Prefabs cannot capture typed entity references outside the captured hierarchy: move the referenced object under the root or clear the reference first.

Custom serialized components declare their scalar UUID reference properties through ComponentSerializationRegistry.RegisterEntityReference(componentType, propertyPattern). A trailing * matches a property-key prefix. Emit reference arrays as separate indexed properties. Opaque strings and asset references are never guessed to be entity references.

Unknown component records are preserved. Scene files retain expanded entity data and an instance baseline, so a missing or failed prefab asset does not delete local objects. Unpack remains available; Apply/Revert/Update require a valid source. Reimporting or renaming an asset preserves its .meta UUID.

Instantiate in C++

#include <Bazzalt/Prefab.h>
#include <Bazzalt/Scene.h>
auto prefab = Bazzalt::Prefab::Load(prefabAssetUUID);
if (prefab) {
    auto object = prefab->Instantiate(scene);
    auto transform = object.GetWorldTransform();
    transform.Position = {5, 0, 2};
    object.SetWorldTransform(transform);
}
// Equivalent: scene.InstantiatePrefab(prefabAssetUUID, parentEntity);

Load returns an optional immutable snapshot of a ready prefab asset. GetUUID, GetName and GetEntityCount describe it. GetInstanceRoot, GetSource and HasOverrides query a linked instance. Refresh and Revert are authoring operations and reject use while gameplay scripts are running. Unpack changes only the local link, not the source file.

Instantiate in Lua

local prefab = Bazzalt.Prefab.Load(assetUUID)
local object
if prefab then
    object = prefab:Instantiate(self.Entity:GetScene())
end
-- Or: scene:InstantiatePrefab(assetUUID, parentEntity)
local root = Bazzalt.Prefab.GetInstanceRoot(object)
local source = Bazzalt.Prefab.GetSource(object)

The source asset UUID is an asset reference, not a filesystem path. Scripts do not author project files or operate the engine loop.

Scripts, cooking and lifecycle

Components are instantiated immediately. During gameplay, attached prefab scripts are initialized at the next safe frame boundary, then receive normal create/update/fixed/late/destroy callbacks. Physics, rendering and GUI use the same components as ordinary entities. A script initialization failure is logged and the failed spawned hierarchy is removed. Scripted instances must be in the active runtime scene.

The editor and game compiler discover native scripts inside prefab assets, even when no instance is placed in a scene. Cooking rewrites their source references to the compiled runtime modules; Lua sources use imported bytecode. Prefab and referenced-asset dependencies are retained by content filtering. Shipped games need no Python code for prefab instantiation.

Current boundaries

Prefab files are bounded to 16 MiB and 10,000 entities. Creating an asset captures a flattened hierarchy; nested prefab composition and variant inheritance are not part of this version. Unpack nested instances before capture, apply, update or revert; these operations reject nested links rather than silently discarding them. Refresh/Revert reconstruct the affected hierarchy: reacquire native Entity handles after these authoring operations, using UUIDs or EntityReference for long-lived references. Preserve component serialization callbacks as deterministic data transformations without external side effects.
