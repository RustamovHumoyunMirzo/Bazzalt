Asynchronous loading and world streaming

Asynchronous loading separates file preparation from changes to the live world. Workers read files and parse scene data. The engine creates components on its owning thread at frame boundaries, so user deserializers, Lua, physics and renderer objects are never constructed on arbitrary workers.

Replace the active scene

#include <Bazzalt/SceneManager.h>
// Store this handle in your behavior; targetScene is an imported Scene asset UUID.
auto request = Bazzalt::SceneManager::LoadSceneAsync(targetScene, false);
// Poll in a later update. Ready means file preparation has finished.
if (request.GetStatus() == Bazzalt::AsyncLoadStatus::Ready)
    request.SetActivationAllowed(true);

The current scene remains active while the replacement is prepared and incrementally instantiated in a detached scene. On successful activation the existing scene unload/loaded events run and scripts restart for the replacement if gameplay was running. A read, parse or component-construction failure leaves the current scene intact. A failure after the actual scene swap, such as a failing script OnCreate, is reported on the handle; the new scene has already become active. Use the UUID overload in packaged games. The path overload supports UTF-8 filesystem paths through std::filesystem.

Add world cells

Bazzalt::Transform offset;
offset.Position = {500, 0, 0};
auto cell = Bazzalt::SceneManager::LoadWorldCellAsync(cellSceneAsset, offset);
// Later, after Complete:
auto root = Bazzalt::SceneManager::GetActiveScene()->GetEntity(cell.GetRootUUID());
// Unload is queued to the next safe frame boundary.
Bazzalt::SceneManager::UnloadWorldCell(cellSceneAsset);

A cell is an ordinary imported .bscene inserted beneath a new parent in the active scene. Its local coordinates compose with the supplied offset. Entity UUIDs are preserved: a conflicting UUID fails the request instead of replacing an existing object. A repeated resident request for the same asset returns its existing operation. Author each distinct cell with distinct entity UUIDs; loading multiple copies of the same cell at different offsets is not supported.

Cell creation is incremental. Geometry and physics components can become visible during Activating; scripts start only once the complete cell is assembled. Treat the cell as unavailable until Complete. Failures/cancellation roll back cell-owned entities. Unrelated objects parented beneath a cell are detached with world transforms preserved during unload. Cell environment, scene extension properties and scene physics settings do not replace the active scene's settings. Native and Lua cell behaviors have their own runtime instances and receive normal update/fixed/late phases. Script assets must already be compiled/imported, including native modules in the game build; loading never invokes a compiler. Missing modules fail explicitly.

Distance-driven streaming

Bazzalt::StreamingCell cell;
cell.SceneAsset = cellSceneAsset;
cell.Offset.Position = {500, 0, 0};
cell.LoadDistance = 150;
cell.UnloadDistance = 220;
Bazzalt::SceneManager::RegisterStreamingCell(cell);
// Update this from your player/controller, on the engine thread:
Bazzalt::SceneManager::SetStreamingPosition(player.GetWorldTransform().Position);

Distance is measured from the supplied streaming position to the cell offset's position. Nearby requests are prioritized. The larger unload distance provides hysteresis, preventing repeated loads at a boundary. At most 1024 cells may be registered; duplicate registration returns false. Unregistering also queues an unload. Update the position as the player moves. Registrations are runtime data and reset when the active scene changes. A failed automatic request remains failed until leaving its unload radius or unregistering/re-registering it; this prevents endless retry loops for broken content.

Budgets and ownership

GetStreamingSettings/SetStreamingSettings control a soft main-thread budget (default 2 ms), entity operations per tick (128), pending requests (64), concurrent file preparations (4), and CPU resource-buffer budget (256 MiB). Invalid settings throw. Work is checked between entity records; a single custom deserializer or GPU upload can exceed the soft time budget. ResourceBudgetBytes accounts for retained raw resource buffers and serialized scene staging reservations, not total ECS/GPU memory or all decoded allocations. Drop unused resource handles/data and unload distant cells to release ownership. Scene YAML has a 64 MiB safety limit.

Read resources asynchronously

#include <Bazzalt/AssetManager.h>
auto resource = Bazzalt::AssetManager::LoadAsync(assetId);
// In a subsequent update:
if (resource.GetStatus() == Bazzalt::AsyncLoadStatus::Complete) {
    auto bytes = resource.GetData(); // shared immutable cooked/cache bytes
}

LoadAsync reads an imported asset's cache file, not its authoring source. It does not compile, decode every file format, or promise GPU residency. Buffers are immutable and remain alive while either the handle or a returned data pointer owns them. Dropping a handle does not cancel its operation. Cancel is cooperative; completed data is never revoked. Scene cancellation is accepted during incremental construction, but returns false once the final scene swap or cell lifecycle commit starts. Check GetError on Failed. Synchronous AssetManager.LoadModel remains available for its existing metadata contract.

Renderer loading and instancing

Interactive editor/game glTF loading prepares files, external resources and picking geometry on the shared job pool, then uses asynchronous texture decoding with main-thread GPU publication. Standalone PNG/JPEG material textures likewise load/decode asynchronously and use a placeholder until ready. Headless/offline renderer construction defaults to deterministic synchronous loading; native tests can explicitly enable its async path. Filamesh/OBJ/FBX runtime mesh loading and environment/HDR construction retain their existing synchronous GPU-facing paths. GPU object creation is not moved to worker threads.

Automatic GPU instancing is enabled by default. Identical procedural primitives share vertex/index buffers, and compatible objects share immutable fallback colors and asset-backed material instances. Repeated GraphicsMesh submissions share geometry/material resources too. Different colors, materials, geometry, render state, skinning or incompatible backend constraints can split batches. Imported model instances are not universally merged: their loader/material ownership still determines eligibility. Picking, selection, entity transforms, LOD and per-view visibility remain per entity. Graphics.SetInstancingEnabled(false) disables automatic batching for diagnostics without changing the scene.

Cells, grids and multiple sources

StreamingCell.HalfExtents describes a world-axis-aligned box centered at Offset.Position. Distances are measured to its nearest edge, not its center. Zero extents preserve point-cell behavior. Priority orders new requests before distance (larger values first), with UUIDs breaking ties. AlwaysLoaded ignores distance. Existing residents are retained through the hysteresis band: load at LoadDistance, unload beyond UnloadDistance.

SetStreamingSource(sourceUUID, position, distanceScale) adds or updates a named source. RemoveStreamingSource removes it. Every enabled source contributes; a cell stays resident while any source retains it. A scale of 2 doubles that source's distance thresholds. SetStreamingPosition remains a convenience source; ClearStreamingPosition removes only that source. Sources are explicit: the engine does not invent a camera or assume the world origin is a player.

StreamingGrid has Origin, CellSize, LoadDistance, UnloadDistance and Cells. Each StreamingGridCell supplies SceneAsset and integer X/Y/Z. Cell centers are Origin + coordinates * CellSize; bounds are half CellSize. RegisterStreamingGrid validates the whole batch before registering anything. Use a distinct scene asset with distinct entity UUIDs for every cell. A cell is a unique world region, not an instanced copy of a scene.

Authoring in scenes

Add WorldCell to a persistent-scene entity and choose SceneAsset. Its world transform places the chunk; HalfExtents is local to this definition and transforms to conservative world bounds. Set load/unload distances, priority and optional AlwaysLoaded. Attach StreamingSource to a player or camera and enable it. The engine discovers these components during Play and standalone gameplay. Editing a scene does not automatically load cells. Components serialize, support enable/disable, appear in Add Component and expose the same C++/Lua controls. Scene references enter asset dependency tracking and packaging.

Duplicate enabled authored definitions for one asset are rejected together. Manual registrations take precedence and report conflicting authored definitions. Definitions inside a streamed cell become active only after their owner finishes activation; removing an owner retires its nested definitions. Disable/remove a definition or unregister a manual cell to keep it unloaded while a source is still nearby. A direct UnloadWorldCell request alone does not disable automatic residency.

Budgets and unload lifecycle

UnloadWorldCell is deferred and changes the handle to Unloading. Poll until Unloaded; IsDone is false while unloading. Behavior runtimes stop once before entity teardown. Entity removal is spread across EntitiesPerTick and MainThreadBudgetMilliseconds, preserving unrelated children that were parented beneath a cell. Activation rollback follows the same bounded removal path. Teardown on engine/scene replacement remains synchronous. Component factories and lifecycle callbacks are indivisible, so the time budget is soft rather than a hard real-time guarantee.

MaxResidentCells (default 128, range 1–4096) caps additive cell slots, including requests and cells still unloading. MaxConcurrentLoads also counts cancelled workers until they exit. Registered definitions are limited to 4096; manual named sources to 256. StreamingSettings.RetryDelaySeconds defaults to 2 (0.1–3600). Automatic failures retain diagnostics and retry after that delay; RetryStreamingCell permits an immediate explicit retry. Repeated requests during unloading return the draining operation instead of creating conflicting copies.

Bazzalt::StreamingCell cell;
cell.SceneAsset = meadowScene;
cell.HalfExtents = {128, 64, 128};
cell.LoadDistance = 100;
cell.UnloadDistance = 150;
Bazzalt::SceneManager::RegisterStreamingCell(cell);
Bazzalt::SceneManager::SetStreamingSource(player.GetUUID(), player.GetWorldTransform().Position);
// Update the source position during gameplay. Engine-owned ticks do the IO and activation.
for (const auto& resident : Bazzalt::SceneManager::GetStreamingCells()) {
    if (resident.Status == Bazzalt::AsyncLoadStatus::Complete) {
        // resident.RootUUID identifies the chunk parent in the active scene.
    }
}

Monitoring and persistence

GetStreamingCells returns copied snapshots with SceneAsset, SceneUUID, RootUUID, Status, Progress, Distance, Automatic and Error. GetStreamingStatistics reports registered/resident/pending/unloading counts, source count and reserved CPU source bytes. GetStreamingEvents returns up to 4096 observed status changes for the most recent pump; reading does not consume them. Poll once per frame and retain any history you need. Events are diagnostics, not a pre-unload save callback. Loaded data becomes usable after Complete, not merely Ready.

Cells contribute entities to the active scene; they do not replace its environment, gravity or active-scene identity. Changes to streamed entities are transient when unloaded. Use the save-game API for persistent gameplay state. Streaming does not automatically serialize modified cells, relocate physics to worker threads, or promise GPU residency when parsing completes.
