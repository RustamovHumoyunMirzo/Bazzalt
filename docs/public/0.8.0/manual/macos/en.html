macOS

BAZZALT has native macOS targets for Intel x64 and Apple silicon arm64. The editor, Hub, compiler and standalone game use the same architecture. macOS 12.0 or newer and a Metal-capable GPU are required. The macOS CI matrix validates Intel and Apple silicon independently.

Install and open a project

Use the Hub package for your Mac. Keep BazzaltHub.app in Applications or another writable installation directory. Hub installs editor payloads under ~/Library/Application Support/BAZZALT/data/Editors/versions. It does not write into its signed application bundle. Default projects live in ~/Documents/BazzaltProjects. Source development uses Python 3.13, PySide6, Xcode Command Line Tools and the matching prebuilt engine SDK. To build the engine itself, download the native filament-sdk-macos-x64 or filament-sdk-macos-arm64 artifact from the macOS CI workflow into deps/filament. These SDKs enable RTTI for reliable C++ exception handling; the stock renderer archive is not a compatible substitute. Large renderer builds run in GitHub Actions.

Game bundles keep executables and native libraries in Contents/MacOS. Cooked content, manifests, encryption keys and license notices belong to Contents/Resources. The player verifies the whole-bundle Apple signature before loading native libraries, then authenticates its resource inventory before loading content.

Native menus and viewports

The editor uses the macOS menu bar at the top of the screen. File, Edit, View, Object, Build, Window and Help use the same actions as other platforms. Preferences and Quit move to the application menu through Qt's native action roles. There is no duplicate menu strip in the editor window. Native Cocoa title bars remain enabled. Scene and Game views present through Metal layers; game code does not receive Cocoa or Filament handles.

Build a game

  1. Open Build > Build Settings.
  2. Select macOS as the target and expand its platform container. Choose the native architecture, runtime SDK folder, Metal or Automatic, bundle identifier, minimum OS version and signing identity.
  3. Keep production metadata, window size/mode, intro, packaging and encryption policy in the shared sections. Each platform retains its own architecture, backend and key-delivery settings when switching targets.
  4. Choose Build or Build and Launch. Output is a .app bundle in the project's bin folder, or a ZIP containing the complete bundle. The game contains native runtime libraries and cooked content, without editor Python.

Build on macOS using a matching native SDK. Use a Mac worker for signed macOS output from another host. Windows/Linux cross output is described in the cross-build guide. Building Intel and Apple silicon releases requires the corresponding editor/compiler and SDK on each architecture. Universal game executables and 32-bit macOS are not produced.

Signing and distribution

The default signing identity is a single hyphen (-), which creates an ad-hoc signature for local development. It is not a trusted publisher identity and does not bypass Gatekeeper. For distribution, install your Developer ID Application certificate and enter its identity. An optional existing notarytool Keychain profile submits and staples the finished bundle. Credentials and private signing keys are never stored in BuildSettings.json. The compiler signs native script modules and runtime libraries before sealing game content, then signs the final bundle. The player validates both the application code signature and the BAZZALT content inventory before loading game libraries.

Keys on the player's Mac

For encrypted packages, choose Player login Keychain in the macOS container. Supply the configured 64-hex-character key environment variable during the build and the first real launch on each player's Mac. Your installer, launcher or entitlement service must deliver this key securely. On that first launch the native game stores the key as a non-synchronizing generic password in the current player's login Keychain. Subsequent launches read that item without the environment variable. Access can still require user authorization if the login Keychain is locked.

Each build has its own account identifier; the bundle identifier scopes the service. Rebuilt games require provisioning for their new build. Package verification uses the supplied environment key directly and never provisions the editor or build machine's Keychain. No game key is written into editor preferences. Keychain protects credentials at rest; it does not prevent an authorized user from inspecting a running game's memory. Embedded, file and environment key delivery remain explicit alternatives.

Development and validation

The macOS 64-bit workflow builds and tests the engine, editor bridge, player and cooker on Intel and Apple silicon. Native Cocoa checks verify menu integration and encrypted bundle integrity on each architecture. If the runner exposes a Metal device, tests also attach and resize a viewport, render a game, check script lifecycle and exercise first-launch Keychain provisioning. Hosted runners without Metal report the GPU checks as unavailable; presentation still needs validation on a Metal-capable Mac. Release packaging produces separate Core, Compiler, Editor and Hub archives. No large dependency build is required on a developer's Windows machine.
