Building a game

A build is a playable copy of your project that does not require the editor. It contains a native Windows executable, the runtime libraries, and cooked game assets. Cooking converts editable assets into runtime products, such as Lua bytecode and compiled shaders. Building a game does not rebuild the engine.

Make your first build

  1. Save every modified scene and stop Play mode. Builds read files on disk, not unsaved inspector values.
  2. Open Build → Build Settings....
  3. In Production, enter the executable name, company, numeric product version, copyright, description, and license text.
  4. In Target, choose Windows x64 or x86. Set Startup scene to a project-relative path such as Assets/Scenes/Starter.bscene. An empty field uses the project's saved startup scene.
  5. Check the runtime directory. Use a prebuilt runtime template matching the engine version and target architecture. The editor distribution includes its x64 template; install the x86 template from the matching Core release when targeting 32-bit.
  6. Choose your window, intro, rendering backend, packaging, and security options, then Apply.
  7. Choose Build, or Build and Launch to run the result. A modal child window shows progress and prevents editing while the external compiler works. Cancel after current step requests a safe stop; a running external tool is allowed to finish. Cancellation before publication keeps the previous build and does not launch it. Once publication begins, cancellation is disabled. Build-only opens a completion dialog with OK and Show in File Explorer. Build and Launch logs completion and the output path to the Console instead.

Game compilation runs in BazzaltCompiler.exe, a separate tool. C++ gameplay scripts require the supported Clang/MSVC-compatible toolchain and the matching target ScriptSDK; Lua-only games do not require a C++ compiler on the user's development machine. Players need neither the toolchain nor Python.

Settings and production metadata

BuildSettings.json lives next to the project's .bproject file and can be committed with your project. It contains no encryption key. Production metadata is written into the executable's Windows version resource and game.json; license text is also written to LICENSE.txt. This does not grant licenses for third-party assets: check their redistribution terms separately.

Windowing supports Windowed, Maximized, Borderless, and Fullscreen (desktop). Fullscreen covers the primary display at its desktop resolution without changing the display mode; it is not exclusive fullscreen. Windowed and borderless sizes use the configured dimensions. Backend choices are Automatic, Vulkan, and OpenGL; availability ultimately depends on the prebuilt runtime and the player's graphics driver.

Startup intro and first frame

The Intro section controls the Powered by Bazzalt screen: enable it, choose its minimum duration in milliseconds and logo height in pixels, and optionally allow skipping by a key press or click. The shared Bazzalt logo is centered on black and embedded in the native player; games do not require Qt, SVG parsing, or a separate logo file.

The startup surface remains black until a rendered frame is ready even when the branded intro is disabled. Loading happens behind the native cover. The minimum intro duration includes loading time, and skipping never bypasses renderer readiness. Gameplay scripts begin at the transition to the game, not during the logo countdown.

Output and intermediate files

Intermediate build products live under .bazzalt/Cache/Build/<architecture>/. Temporary cooking folders are removed after a build succeeds or fails. Later builds also reclaim marked folders left by a crashed compiler; older unmarked caches are preserved. Incremental script products remain available for the next build. A normal build is published to bin/<name>-windows-<architecture>/. With Publish as a ZIP archive enabled, the final deliverable is bin/<name>-windows-<architecture>.zip. The ZIP contains the executable, libraries, metadata, license files, and all game content. Extract it before running the game.

Build and Launch with ZIP output retains one extracted launch copy in the build cache, not an executable inside the ZIP and not a new permanent copy for every build. Output replacement is restricted to compiler-owned output; a failed cook or verification keeps the previous published build. Do not manually remove ownership markers while rebuilding to the same location.

Content and dependencies

By default, all indexed project assets and scenes are included. Packaging provides Included asset patterns and Excluded asset patterns, with one project-relative wildcard pattern per line. The default included pattern, **, keeps everything. For example, include Assets/Scenes/Main.bscene and Assets/Dynamic/** to keep your main scene and assets your scripts load dynamically. Patterns use forward slashes and match the full project-relative path, without Gitignore-style negation.

The startup scene is retained. References in serialized scenes, material instances, mixers and texture descriptors retain their dependencies even when those dependencies do not match an inclusion pattern. Explicitly excluding a required asset is an error. The compiler cannot predict an asset name assembled by game code, so keep dynamically loaded assets explicitly. Filtering applies to cooked output after import and script validation: an invalid import can still stop the build even if its output is excluded.

Lua source and C++ source are not included. Lua bytecode, compiled C++ modules, imported meshes, materials, textures, audio, and environment products are included as applicable. Custom shaders are compiled during cooking rather than by the player.

The native player opens an immutable cooked asset index. It does not scan sources for imports, start the editor, load Qt, or execute Python. Core, GUI, and Lua runtime libraries sit beside the game executable. The compiler itself may contain a packaged Python implementation; it is a development tool and is never copied into a game.

Security options and their limits

Security provides Low, Medium, High, Very high, and Custom profiles. These are convenience presets, not protection guarantees. Every build has a signed content inventory. Low leaves content unencrypted. Medium adds AES-256-GCM with a recoverable executable delivery key. High and Very high use an external environment master key and different chunk sizes; they have the same cryptographic strength. Every encrypted build gets a fresh data key, separate from its delivery key. Presets do not add padding automatically. You may customize the individual settings.

Content format is either loose files or versioned BPAK v3 packages. Packages compress segments when that makes them smaller, before encryption, and store byte-identical files only once as payloads. Already compressed images, audio and models may shrink little. Chunk size is a maximum-size target, not a compression ratio. Decoded segments are at most 4 MiB plus framing; minimum-size chunks have a small framing overhead. Encryption requires BPAK. A compatible version-3 runtime template is required; older templates are rejected with an error rather than producing an incompatible game.

AES-GCM uses fresh nonces and authentication tags for package data and encrypted asset paths. Keyed digests avoid exposing plaintext content fingerprints. The compiler rejects unsafe paths; the player checks authentication, complete-file hashes, lengths, ordering, duplicate-file references, decompression sizes, and extraction limits before loading content.

Encrypt configuration and inventory is enabled by encrypted presets. It protects the game settings and asset inventory with separate authenticated encryption keys. The player decrypts them in memory; it does not write plaintext copies beside the executable. A small signed bootstrap remains readable so the player can locate the right key. Build IDs, encryption options, package sizes and installed file counts are not secret.

The compiler signs the bootstrap and inventory containing configuration, game content, libraries and license-file hashes. It also checks the player executable and key seal, and checks complete decoded files after extraction. Verified files are kept read-only through operating-system file locks while in use. The verification key is embedded in that game's executable; the private signing key exists only during the build and is not shipped. The player rejects modified, missing or unexpected files before initializing the engine. Keep saved games and logs outside the build directory. These signatures do not establish publisher identity or stop an attacker who can replace the executable and its verification code. Publisher code signing remains a separate release step.

Key delivery can be an executable overlay, a sibling game.key file, or an external environment variable. Embedded and sibling keys can be extracted by anyone with the build. For an environment key, set the selected variable to a 64-character hexadecimal AES key before building and before launching the game. Keys are not saved in build settings or printed to the Console. Plan key provisioning before sharing an environment-key build.

Generate a random key with BazzaltCompiler.exe --generate-key (or python -m Compiler.build --generate-key in a source checkout). This explicit command prints a secret: keep its output out of build logs and source control. Do not substitute a password, repeated characters, or an all-zero value for a cryptographically random key.

Windows account-bound key delivery is available for private/local builds. Windows DPAPI protects its delivery key instead of shipping a plaintext key. Such builds normally require the Windows account and machine that built them; do not choose this option for a game you want to distribute to other players. For portable protected builds, use external provisioning. Anyone authorized to run the game can still inspect its decrypted process memory.

Packages are extracted into a unique temporary directory for play, with Windows access restricted to the launching account and SYSTEM, and removed on normal exit. A later player launch cleans marked abandoned directories after a crash, while leaving active sessions and unowned folders alone. Plaintext exists during play and may remain after a crash until that cleanup runs. Fully streaming assets without extraction is not implemented. Encryption does not protect against a player controlling the process or reading memory. Random decoy padding only changes the package footprint. It is not DRM, signing, anti-cheat, or a replacement for a trusted server.

Before distributing

  • Test the exact output on a clean Windows machine, including audio, input, scene changes, and rendering.
  • Use matching x86 or x64 libraries; a 32-bit game cannot load 64-bit native script modules.
  • Review third-party license notices and all included assets. Keep the supplied runtime notices.
  • Sign your final executable after version resources and embedded keys have been written. Signing and installer generation are separate release operations.
  • Back up external encryption keys securely. Changing or losing a key can make an existing encrypted build unusable.

Target platform

Select Windows or Linux in Build Settings. Build on the matching OS with a matching runtime template. Windows supports x64 and x86 output; Linux supports x64/x86 and uses an executable without an extension. Unsupported selections display a warning, and build attempts stop with a Console error. See the Linux guide for dependencies and deployment.

Independent platform profiles

Target selects the platform used by the compiler. Expand Windows, Linux or macOS to configure architecture, runtime template, backend and key storage independently. Shared metadata, startup scene, windowing, intro, packaging and encryption policy remain outside these containers. macOS adds bundle identifier, minimum version, signing and notarization fields. See macOS builds and player Keychain storage.
