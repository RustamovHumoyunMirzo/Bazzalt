SSH build workers

Build > Remote Build sends a project snapshot to a worker you control, invokes its standalone BazzaltCompiler, and optionally downloads the completed game archive. The worker builds natively for its own OS. This provides Windows, Linux and macOS output from any supported editor host without embedding a cloud service or engine build in the editor.

Prepare a worker

  1. Create a dedicated non-administrator build account on the target OS and enable SSH/SFTP.
  2. Install the matching BazzaltCompiler package with its BazzaltCooker and Filament tools. Install the desired target Core runtime SDK. No editor window is required on the worker.
  3. Install the native C++ toolchain if the project uses C++ behaviors, subsystems or source extensions. Provision any required extension packages in the worker's extension store.
  4. Verify the worker's SSH host-key fingerprint through a trusted channel. Add that verified key to your normal OpenSSH known_hosts file, or provide a dedicated known-hosts file in the profile.
  5. Provision publisher signing credentials, macOS notarytool profiles and game-build environment keys on the worker when required. These are not copied from editor preferences.

Workers compile trusted project code under their account's privileges. This is not a sandbox for untrusted submissions. Prefer a dedicated account or disposable VM, with access limited to the project workspace and required signing credentials.

Connection profile

Give the profile a label, host address, SSH port (22 by default), username and worker OS. The OS chooses a safely quoted POSIX command or encoded PowerShell command. Select SSH key/agent or password authentication. The private-key picker opens the native file chooser; its optional passphrase is separate from the key file. Passwords are masked.

Unknown host keys are rejected. Test connection never silently trusts a new key. It authenticates and asks the actual compiler for its worker-protocol and host information. The status text uses the editor's success/error colors. If the connection is refused, verify the server address, port, account, host key and compiler executable path.

Credential storage

Credentials stay in memory for the current dialog unless Save credential in OS vault is enabled. That option uses a native Windows credential store, macOS Keychain, or a Linux Secret Service/KWallet backend. Plaintext keyring backends are rejected. If no usable vault is available, disable saving and enter the credential for the session. Profiles are stored in the editor's per-user app-data settings, without passwords or passphrases; they are not project files.

Workspace and tools

Test Connection checks SSH authentication, the compiler protocol, the native cooker version and the runtime SDK. It also reports the detected C++ compiler version; content/Lua-only projects can build without a C++ compiler. Set the runtime override when your SDK is outside the compiler's RuntimeTemplates directory. Build checks the selected game architecture before uploading.

Remote working directory is an existing directory accessible to the build account. The editor creates a .bazzalt-remote area beneath it. Each transferred request has its own identifier; persistent project inputs are separated by a project identity. The remote compiler executable can be on PATH or specified as an absolute path. Runtime SDK and script-compiler overrides refer to paths on the worker, not the editor machine.

Use native SDKs on workers. The worker overrides a local cross-build method with native compilation. For macOS distribution, its signing identity and optional notarytool profile come from the project's macOS platform settings, while certificates and credentials remain installed on the Mac.

Sync and clean options

Sync all assets sends the full project inputs. Disable it only after a successful full sync to reuse existing asset data while updating scripts, headers, metadata and scenes. A clean workspace requires a full asset sync. Removed files are tracked through a transfer manifest, so full syncs remove previously transferred inputs that no longer exist. The tool never deletes unrelated worker files.

Git metadata, local build caches and bin output are excluded. Default credential exclusions include .env, *.pem, *.key and .ssh paths; customize the comma-separated globs when needed. Symlinked inputs, unsafe archive paths, duplicates and oversized transfers are rejected. The current transfer limit is 32 GiB and 500,000 files. Cache files and previous game outputs are not recursively uploaded.

Build, cancel and retrieve

Save scenes and stop Play, then choose Build on worker. Work occurs on a background thread while the dialog blocks edits to the main editor. Cancellation is checked during local packaging/transfers and forwarded to the worker compiler, which stops before publication after its current safe build step.

Download game archive checks the received file's size and SHA-256 before publishing it under bin/Remote with a unique filename. Leave on worker keeps the completed archive there. Open output folder on worker asks that machine's OS to reveal it; a headless server may not have a file manager. The result status includes the output location.

Delete intermediate files removes the worker's build cache after success, while persistent inputs remain available for incremental sync. Failed builds retain the previous published game. Transient upload/request files are cleaned up when the connection permits it. SSH transport authentication and checksums protect the transfer; the packaged game also retains its own signed inventory and encryption policy.

Player keys versus worker credentials

SSH credentials authenticate the build connection. Game-encryption keys and publisher signing credentials are separate. Mac player Keychain provisioning still occurs only on the player's first real launch; package verification does not save player keys on the build worker. Windows account-scoped DPAPI binds data to the builder account and is rejected for automatically downloaded remote output. Use embedded, file, environment or player-Keychain delivery as appropriate for distribution.

Troubleshooting

A host-key error means the worker has not been trusted, or its key changed. Verify the fingerprint before updating known_hosts. A missing compiler error means the remote executable is absent from PATH or the override is wrong. Runtime version/architecture errors require a matching SDK, not a different display label. Missing extension errors require installing the referenced package on the worker. Signing/notarization failures must be repaired in the worker account's certificate/Keychain configuration.
